# 01 — Product strategy and value proposition

## Product thesis
A native workspace where teams convert conversation into accepted work, with agents operating under explicit authority across local and cloud environments. Communication is familiar; shared execution and low-friction review provide the switching incentive.

Do not position the product only as "Slack with bots" or "a multiplayer coding agent". The wedge spans the whole product team. The developer keeps a preferred editor. The designer sees a preview. The product manager sees acceptance criteria. A reviewer sees evidence, not raw agent narration. All participants share the same task and decision history.

## Initial customer and jobs
The initial team already uses team chat, source control, issue tracking, and coding agents. Its pain is not a lack of generated text. It is repeated context setup, unclear ownership, private agent sessions, noisy status updates, uncertain permission boundaries, and hard-to-review outputs.

The main job is: "Help us turn this request into a result another teammate can confidently accept without reconstructing everything." Secondary jobs include understanding why a change happened, taking over blocked work, coordinating bounded parallel attempts, and repeating a workflow that worked.

## The differentiating bundle
A **work contract** records desired outcome and permitted means. A **workroom** is a coordinated view of task, conversation, runs, artifacts, and approvals. A **review package** makes changes and evidence inspectable. An **attention inbox** routes decisions and blockers rather than every machine event. An **environment switch** makes execution/model locations visible and supports checkpoint continuation where tested.

Each part must be useful on its own; the advantage comes from coherent transitions between them. Context should not be re-entered when a message becomes a task or when a task becomes a review. Permissions should not be silently widened by those transitions.

## Experience principles
Familiar before novel: daily chat remains obvious. Progressive disclosure: advanced execution detail is available but not mandatory. Calm by default: machine activity is collapsed unless it matters. Explicit accountability: a human owns shared delegated work. Inspectable automation: sources, scope, changes, and unresolved questions remain visible. Local responsiveness: ordinary interaction does not wait for a model. Reversible where possible: changes are proposals until accepted; irreversible operations are labeled.

## Signature demonstration
A support report describes confusing checkout behavior. Product turns it into a bounded task, with a precise outcome and no production access. An agent reproduces the issue in an isolated workspace, creates a patch and preview, and records checks. Design comments on wording in the browser. Engineering reviews the diff. The accepted artifact version becomes a pull request after separately authorized publication. The channel shows meaningful milestones, not token output. A teammate joining later can understand the request, evidence, and decisions in one place.

Measure the entire demonstration with ordinary users. A founder narrating every click is not evidence of usability.

## Adoption mechanism
Deliver value alone before demanding a workspace move. A new user connects one approved project, performs one bounded task, and shares a review link with one teammate. The project becomes a habitual shared space. Only then does broader messaging migration become justified. Browser review and low-friction invitation are part of the core adoption path, not optional extras.

## Competitive discipline
Maintain a quarterly evidence-based comparison using first-party product documentation and actual user testing. Do not assert that agent assignment, native UI, shared review, or cross-app actions are unique. Compete on end-to-end quality and reduced human effort. The durable advantage is a reliable, permission-aware relationship between conversation, execution, and accepted evidence—not lock-in to one model.

## Validation and stop rules
Use the same defined unit of work before and after adoption. Record accepted outcomes, review time, rework, costs, interruptions, and failure causes. Keep failed eligible tasks in the denominator. Expand after teams repeatedly return without founder assistance and pay for the workflow. Reconsider the wedge if users praise the demo but keep reviewing and coordinating elsewhere. Do not compensate for weak retention by adding more agents or broadening the market prematurely.
