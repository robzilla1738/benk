# ADR-005 — Tasks, runs, versions, and approvals are distinct

**Status:** Accepted — domain model
**Date:** 2026-10-08
**Owner:** founding technical/product lead

## Context
The product must combine a fast native collaboration experience with inspectable, bounded local/cloud execution. This decision narrows implementation ambiguity while preserving the user's fixed requirements. Read the linked domain/security specifications before treating a mechanism as complete.

## Decision
A task describes the desired outcome and accountable human. A contract revision bounds its execution. A run is one attempt. An artifact version is an immutable output. An approval authorizes one exact proposal, and an acceptance records human evaluation of a particular result against a contract. A workroom is a coordinated view of these objects, not an independent permissions silo.

## Consequences and alternatives
More explicit objects require careful UI composition, but prevent chat messages from ambiguously carrying authority. Run success never implies task acceptance. Artifact edits create new versions; old approvals do not silently authorize them. Reopening an accepted task requires a guarded revision and preserved history.

## Validation and revisit trigger
Gate: state-machine fixtures and command-specific transactional guard tests. Reducer edge tests alone do not prove authorization, human review, or current revision. A schema-valid action may still be forbidden by its contract. Changes to these identities or lifecycle semantics require migration and compatibility plans.
