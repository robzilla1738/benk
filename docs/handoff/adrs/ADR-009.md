# ADR-009 — Exact approvals and external-action intents

**Status:** Accepted — safety invariant
**Date:** 2026-10-08
**Owner:** founding technical/product lead

## Context
The product must combine a fast native collaboration experience with inspectable, bounded local/cloud execution. This decision narrows implementation ambiguity while preserving the user's fixed requirements. Read the linked domain/security specifications before treating a mechanism as complete.

## Decision
Before an external side effect, persist an intent bound to actor/workspace, contract revision, action payload digest, artifact version, destination, policy revision, budget reservation, and coordinator generation. Approvals reference that exact proposal and are revalidated/consumed atomically where applicable. Current authorization is checked again at dispatch.

## Consequences and alternatives
External APIs differ in idempotency and receipt behavior. Use stable provider keys where supported. A timeout after submission means unknown until reconciled, not permission to retry blindly. Keep the user-visible state honest. Agents may request approval but cannot impersonate a human approver or grant themselves capabilities.

## Validation and revisit trigger
Gate: changed artifact, changed policy, expired approval, replay, mismatched tenant, stale generation, insufficient quorum, and concurrent consumption tests. A database transaction cannot roll back an external email or deployment; define provider-specific reconciliation and compensating actions before enabling the integration.
