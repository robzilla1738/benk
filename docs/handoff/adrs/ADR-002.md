# ADR-002 — Effect application services

**Status:** Accepted — user-fixed stack
**Date:** 2026-10-08
**Owner:** founding technical/product lead

## Context
The product must combine a fast native collaboration experience with inspectable, bounded local/cloud execution. This decision narrows implementation ambiguity while preserving the user's fixed requirements. Read the linked domain/security specifications before treating a mechanism as complete.

## Decision
Use TypeScript and Effect for cloud application services and the local agent engine. Services expose typed domain failures, bounded concurrency, explicit resource lifetimes, and controlled cancellation. HTTP, IPC, provider, and database adapters remain thin. Pure domain rules may be framework independent to support shared golden fixtures and Rust parity.

## Consequences and alternatives
Effect 4 is the selected baseline; exact compatible packages and actual lockfiles must be established in the implementation environment. Isolate unstable APIs and external integrations behind internal service boundaries. The native UI must not wait for the Effect engine for cached interaction.

## Validation and revisit trigger
Gate: typecheck the dependency-backed scaffold, test expected error channels and cleanup, and prove overload cannot starve interactive requests. Never instantiate an application runtime per request or use unbounded detached work. Revisit individual unstable modules on evidence without removing the fixed Effect architecture.
