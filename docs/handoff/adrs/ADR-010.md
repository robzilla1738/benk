# ADR-010 — Checkpoint handoff with fenced ownership

**Status:** Accepted — portability scope
**Date:** 2026-10-08
**Owner:** founding technical/product lead

## Context
The product must combine a fast native collaboration experience with inspectable, bounded local/cloud execution. This decision narrows implementation ambiguity while preserving the user's fixed requirements. Read the linked domain/security specifications before treating a mechanism as complete.

## Decision
A run has one authoritative coordinator and generation at a time. Shared execution normally has cloud coordination even when tools run locally. Private offline work may have local authority. Handoff transfers a verified safe checkpoint and changes ownership by compare-and-set; the previous generation loses mutation authority.

## Consequences and alternatives
A checkpoint includes source references, versions, artifacts, adapter identity, environment definition, approved context, and secret handles—not raw secret material. Arbitrary live process or opaque provider-session migration is out of scope. A hung or partitioned old runner may still physically exist; broker leases and fencing must constrain its effects.

## Validation and revisit trigger
Gate: no in-flight irreversible action, verified artifact transfer, adapter compatibility, generation monotonicity, stale runner rejection, repeated handoff, cancellation, and partition recovery. Unknown external effects block handoff until reconciled. UI must say checkpoint continuation rather than promise seamless process migration.
