# ADR-013 — Evidence-gated delivery and dependency provenance

**Status:** Accepted — delivery policy
**Date:** 2026-10-08
**Owner:** founding technical/product lead

## Context
The product must combine a fast native collaboration experience with inspectable, bounded local/cloud execution. This decision narrows implementation ambiguity while preserving the user's fixed requirements. Read the linked domain/security specifications before treating a mechanism as complete.

## Decision
Build in bounded tickets with explicit requirements, acceptance scenarios, and evidence paths. Keep a tested reference core separate from unverified scaffolds and from implemented product features. Dependencies use exact recorded versions and generated lockfiles after actual resolution. Signed releases, rollback, SBOM, and license review are delivery controls, not marketing claims.

## Consequences and alternatives
The ZIP is a build handoff, not a working product or compliance certification. Baseline tests validate selected invariants, not a production distributed system. No fake lockfiles, invented CI screenshots, placeholder secrets presented as credentials, or simulator results labeled model executions. Do not auto-install or deploy into a user's accounts without authorization.

## Validation and revisit trigger
Gate: independent review of actual builds, tests, failure behavior, package contents, and release provenance. Upgrades require compatibility/replay tests. Any unsupported external dependency is reported plainly with a reproduction command and a bounded next action. Full parity and performance claims need their own evidence.
